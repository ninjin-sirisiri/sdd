# 設計面談の質問・回答履歴と仕様書の保存前確認

**Classification:** architectural

**Chosen approach:** OpenCode V2 の構造化フォームを使い、ホストのイベント購読 hook で質問と回答を記録する。ローカル検索 CLI から原記録を取り出し、`sdd-design` が保存前に仕様案と照合する。自由文の会話からモデルに組を推測・転記させる方式や、セッション全文を保存する方式は採らない。

## 目的と対象外

- 重要な質問を省いて仕様書を書いたり、明示された回答と異なる仕様を保存したりしない。一方で、[以前の判断基準](2026-11-07-skill-judgment-and-handoff-design.md)が減らした、確定事項の聞き直しや可逆的な実装詳細の確認は増やさない。
- 同じ checkout 内で、記録を有効にした後の全 `sdd-design` セッションの設計質問と回答を参照できるようにする。導入前の履歴はユーザーが指定したログだけを取り込む。
- 初版の自動記録は OpenCode V2 のみ。Claude Code・Cursor の記録、別 worktree・別マシン・チーム共有、他のリポジトリの会話収集、意味検索の外部サービスは対象外。既存 spec／roadmap の一括更新や、既存の HTML・実装承認手順の変更も行わない。

## アーキテクチャと責務

- `skills/sdd-design/SKILL.md` が全ホスト共通の質問方針、履歴が使える場合の検索と照合、保存前の確認、既存文書の更新条件を持つ。`README.md` に OpenCode V2 でのリポジトリ単位の有効化と検索・取り込み手順を案内する。
- `adapters/opencode/` の V2 サーバープラグインが設計用の質問をネイティブフォームとして提示し、`form.created`、`form.replied`、`form.cancelled` を購読する。プラグインが登録した設計フォームに限定し、ホストのセッション ID・フォーム ID・項目 ID で結びつける。登録された設計案件と現在の checkout を照合し、他のセッションの一般フォームや別リポジトリのイベントを混ぜない。既存の HTML 用プラグインとは責務を分ける。
- 共通の履歴処理は `scripts/sddlib/` に置き、利用側リポジトリの `.sdd/design-history.sqlite3` にトランザクションで保存する。保存先が Git の除外対象で未追跡であることを作成前に確認する。満たさなければ設定方法を案内し、記録を開始しない。
- `scripts/design-history` の検索は読み取り専用とし、設計案件、質問 ID、日本語を含む部分一致で絞り込める。検索語は質問本文・選択肢・回答に照合する。結果は該当する組を JSON で返し、設計案件、出所、状態、質問と選択肢、回答が同時に読めるようにする。終了済みログの取り込みは検索とは別の、ユーザーの明示操作とする。

## 質問から文書保存まで

1. リポジトリと既存文書を調べ、履歴が使える場合は該当する案件を検索する。利用者向けの振る舞い・受入条件・重要な制約・後工程の契約など、答え次第で設計が変わる未合意点だけを聞く。選ぶ意味のある場合は選択肢・おすすめ・理由を示し、自由回答も受け付ける。独立した論点はまとめ、依存する論点は順に聞く。質問数の最低・上限や、節ごとの承認は設けない。
2. hook は、質問本文・提示順の選択肢・実際の選択値または自由回答を原記録として保存する。同じ選択肢名を持つ別の質問を混同しない。取消・未回答・保留は合意と区別し、後の訂正は元の回答を上書きせず別の回答として扱う。どの判断を訂正したか不明なら、最新というだけで採用しない。モデルは原記録を書き換えず、回答の解釈を本人の発言や承認として扱わない。
3. 過去分は、ユーザーが指定したローカルのログを対象に、案件と取り込む組を事前に確認できるようにする。元の質問・選択肢・回答の対応が確かめられる組だけを取り込み、手がかりが足りない組は理由を示して除外する。元ログは変更せず、取り込み由来であることを記録する。全セッションの探索や、会話全文の複製はしない。
4. 新規 spec／roadmap の Markdown を書く前に、予定する内容を関連する原記録と照合する。目的・完了条件・対象外・重要な制約をチャットで一度示し、roadmap では分割と順序も示して明示確認を得る。重要な未決事項は影響と解消時点を示し、決まった事実として書かない。未合意点がなければ追加の質問は作らない。保存後の文書レビューや実装承認は、この確認で代用しない。
5. 既存の spec／roadmap は、対象・変更する意味・依存する作業への影響について明示的に合意するまで書き換えない。履歴は合意を照合する根拠であって、承認済み文書に代わる仕様の正本ではない。共通契約の変更は、合意後に所有する spec から反映する。実在する spec へのリンク追加など、意味を変えない更新には再承認を求めない。

## 記録できない場合

- hook の未設定・停止、書き込み失敗、イベントの欠落と、該当する履歴がないことを区別する。記録を有効にしたセッションで必要な回答を取得できない場合は、その回答を前提とする spec／roadmap の保存を止め、欠けている内容と回復方法を伝える。モデルに後から回答を書き足させない。イベントの再配信や同じログの再取り込みで組が重複しないようにする。
- 記録非対応のホストや未有効の利用側では、自動記録がないことを明示し、現在の会話と承認済み文書を使って保存前の確認を行う。共通の保護手順は省略しない。
- 設計質問に秘密値を求めない。記録・取り込み対象は設計の質問と回答に限り、秘密情報を検出した組は保存対象から外して欠落を通知する。添付ファイル、資格情報、ツール出力、セッション全文は保存せず、履歴を外部サービスに送信しない。Git の除外はアクセス制御ではないことを案内する。

## 検証と完了条件

- 使い捨てのリポジトリと実際の OpenCode V2 で、選択回答と自由回答がモデルによる転記なしで保存され、別のセッションから案件・日本語キーワード・質問 ID で取り出せることを確認する。公開 API でイベントが定義されていることだけでは合格としない。実機でのイベント識別・回答取得を、記録機能の完了判定前に確認する。
- 自動テストで、複数質問の対応、取消・未回答、再配信、別リポジトリの除外、Git の除外条件、入手できない回答の扱い、過去ログの重複・曖昧な組の除外、検索の絞り込みを確認する。
- 設計面談を試用し、「削除は取り消せる」という回答に反する案や、既存文書への未承認の意味変更が保存前に止まることを確認する。明確な要求の対照ケースでは不要な質問を増やさず、リンク追加だけで再承認を求めないことも確認する。自動テストとモデルの試用結果は区別して記録する。
